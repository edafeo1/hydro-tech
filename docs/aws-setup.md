# Set up staging in your AWS account

Account ownership decision: **Edafe's AWS account**, as requested. The AWS connection verified account `385427225795`, and staging has now been deployed. See [the current deployment record](aws-staging-status.md). The guide below describes first-time setup; use the existing `hydrotec-staging` stack for this deployment rather than creating a duplicate. The current stack has `EnableGitHubDeployment=false` because the account's organisation policy denied the IAM provider check. Optional GitHub role setup requires that permission issue to be resolved first.

## 1. Sign in and download the template

Sign in to your AWS account with an identity allowed to create CloudFormation, S3, CloudFront and IAM resources. Open [CloudFormation in Sydney](https://ap-southeast-2.console.aws.amazon.com/cloudformation/home?region=ap-southeast-2#/stacks/create).

While signed in to GitHub, open [`infrastructure/aws-static-site.yml`](https://github.com/edafeo1/noxy/blob/main/infrastructure/aws-static-site.yml) and use **Download raw file**. The repository is private, so an unauthenticated raw URL will not work.

Before creating the stack, check [IAM → Identity providers](https://console.aws.amazon.com/iam/home#/identity_providers) for `token.actions.githubusercontent.com`. If it exists, copy its ARN and confirm its audience includes `sts.amazonaws.com`. Reuse it rather than creating a second provider for the same URL.

## 2. Create the staging stack

Choose **Create stack → With new resources (standard)**, select **Upload a template file**, and upload the downloaded YAML. Use these settings:

| Setting | Value |
|---|---|
| Region | Sydney / `ap-southeast-2` |
| Stack name | `hydrotec-staging` |
| `CustomDomainName` | Leave empty |
| `CertificateArn` | Leave empty |
| `EnableGitHubDeployment` | `true` |
| `ExistingGitHubOidcProviderArn` | Existing GitHub provider ARN, or empty if none exists |
| `GitHubOidcSubject` | Keep the supplied default unless this repository uses a custom subject |

Review the resources and acknowledge that the template creates IAM resources, then submit. It creates a private versioned S3 bucket, a CloudFront distribution and its routing/security policies, and a deployment role limited to that bucket and distribution. If needed, it also creates the GitHub OIDC provider. AWS usage is billed to your account. The CloudFront staging hostname is publicly reachable when files are uploaded; search indexing remains disabled. This is separate from the private design preview.

Wait for `CREATE_COMPLETE`, then open the stack's **Outputs** tab. Account-specific resource names are generated by AWS; no account number needs to be entered into the template. If the stack fails, inspect **Events** before retrying so an existing provider or partially created stack is handled correctly.

The template's default trust subject is `repo:edafeo1@20019420/noxy@1438595013:environment:staging`. GitHub reports this repository was created on 29 October 2026, after the immutable-subject rollout. That default follows GitHub's documented format; it has not yet been compared with a live workflow token. If the repository's OIDC settings have a custom subject, use its exact value instead. Do not broaden trust to a wildcard.

## 3. Connect the GitHub deployment

In [repository settings](https://github.com/edafeo1/noxy/settings/environments), create a `staging` environment and restrict its deployment branches to `main`. Configure any available reviewer rules you want. Then add these **repository Actions variables** under [Settings → Secrets and variables → Actions → Variables](https://github.com/edafeo1/noxy/settings/variables/actions):

| GitHub variable | Value from the CloudFormation Outputs tab |
|---|---|
| `AWS_REGION` | `AWSRegion` |
| `AWS_STAGING_ROLE_ARN` | `GitHubStagingRoleArn` |
| `AWS_STAGING_BUCKET` | `BucketName` |
| `AWS_STAGING_DISTRIBUTION_ID` | `DistributionId` |
| `AWS_STAGING_ORIGIN` | `WebsiteUrl` |

Finally, set the **repository** Actions variable `AWS_STAGING_ENABLED` to `true` in the same settings screen. Keep this enable switch at repository level because GitHub evaluates the job condition before loading environment-level variables.

These output values identify resources; they are not passwords or access keys. You can provide the outputs for help checking the configuration. No AWS credentials belong in this chat or the repository.

## 4. Run and verify

Open [Actions → Deploy AWS staging](https://github.com/edafeo1/noxy/actions/workflows/deploy-staging.yml), select **Run workflow**, and run it from `main`. It builds and checks the website, obtains short-lived credentials, uploads the files and requests a CloudFront cache invalidation. It does not create infrastructure or modify DNS. A successful workflow confirms the upload and invalidation request, not that global cache propagation is finished.

Open `WebsiteUrl` and check the homepage, a service URL directly, the gallery, contact review/email-draft flow, capability PDF and an unknown URL's 404 response. The contact form still opens an email draft; automatic enquiry delivery is separate work.

The business domain, certificate, DNS changes and production indexing come after staging has been checked. The existing staging resources and completed checks are recorded in `aws-staging-status.md`.

## Lifecycle and references

The versioned S3 bucket and any GitHub OIDC provider created here are retained when the stack is deleted. Record their names/ARNs. Reuse a retained provider on a future stack; removing retained resources is a separate action. Deleting the stack removes its generated deployment role and distribution.
